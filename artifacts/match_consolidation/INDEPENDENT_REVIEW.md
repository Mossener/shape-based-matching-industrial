# Independent review: match consolidation

This is a read-only review of the deterministic consolidation change at the
current working tree. It covers `line2Dup_matches.hpp`, its call site in
`line2Dup.cpp`, `tests/match_consolidation_test.cpp`, and
`artifacts/match_consolidation/verify.cpp`. I did not edit core code, run the
verification binaries, or use held-out image results to choose behavior.

## Result

The consolidation helper is logically equivalent to the intended duplicate
contract for finite matcher outputs:

1. It orders matches by descending exact `float similarity`, then class, y, x,
   and template ID.
2. `std::unique` uses `Match::operator==`, whose key is class, x, y, and exact
   similarity. Because the first sort groups equal keys and puts the smallest
   template ID first, the retained representative is the minimum template ID.
3. It reorders the retained records by descending score, then template ID, class,
   y, x. This makes ties independent of OpenMP merge order while preserving
   every retained score, class and coordinate.

The hand test covers 300 shuffled input orders, class/position/score separation,
lowest template ID, exact adjacent scores, empty input, singleton input, and
idempotence. The independent verification oracle groups into a map keyed by
class/x/y/score, chooses the smallest template ID, and applies the same final
priority independently of the production helper. That is a sound oracle shape:
it does not call the helper or choose IDs from a current output.

The core call site performs consolidation once after all class/template search
and before `search_ms` is stamped, so duplicate removal is included in the
search interval. No pre-filter, candidate truncation, score recomputation,
bounding-box operation, or template-bank mutation occurs at this call site.

## Score and duplicate semantics

- Scores are compared as exact `float` values. The helper does not round, cast,
  threshold, or recompute them. `std::unique` therefore merges only bitwise
  equal normal matcher scores in the usual finite case; the oracle stores float
  bits to make this explicit.
- The duplicate key correctly excludes `template_id`, so equal class/x/y/score
  records collapse and the first record after the grouping sort is the minimum
  template ID.
- The key correctly includes class, x, and y. Two classes, two positions, or
  unequal scores remain separate even when their template IDs match.
- The final tie order uses template ID before class/y/x. This is a deterministic
  output-order contract, not a change to duplicate membership.
- `Match::operator==` also excludes template ID by design. The first sort is
  essential; replacing it with a different sort or invoking `unique` directly
  would be incorrect.

For production matcher values, scores are generated by integer response maps or
the existing floating argmax and are finite. The helper does not define a useful
ordering for NaN: comparisons with NaN are false and `std::unique` treats NaNs
as unequal. If public API callers can inject arbitrary `Match` values into this
helper in future, document finite-score preconditions or add explicit NaN policy.
Current `Detector::match` does not expose a mutable match vector, so this is a
generic-helper limitation rather than a current matcher regression.

## Output and bounding-box contract

The helper mutates only vector order and removes duplicate vector elements. It
does not modify x, y, score, class ID, template ID, or any shape/template data.
The current matcher returns `Match` records; therefore no bounding box can be
changed by consolidation itself. An adapter deriving a box from x/y/template
metadata will see the minimum template ID representative for a duplicate key,
but that representative has the same class, x, y and score. If an adapter uses
template ID to select a different silhouette or box, its box may change even
though matcher-level semantic keys remain equal. Such adapters need an explicit
minimum-template-ID contract or a template-independent box rule.

The final sort can change ordering among otherwise equal-score, nonduplicate
records. Callers must not infer a different detection priority from the old
OpenMP reduction order. The verification's `full_ordered_equal` check is right
to require the new deterministic order for stable calls; semantic-set checks
alone would miss this contract.

## Threading and both local paths

`consolidateMatches` runs after the OpenMP template loop has joined and the
reduction vector is local to the caller. It has no shared worker state and is
serial, so the helper itself is thread-safe for independent calls. The existing
per-worker local refinement paths (fused SSE path and map-plus-argmax fallback)
produce the input vectors before this point; consolidation does not distinguish
which path produced a record.

The hand test does not exercise either local path; it tests only vector semantics.
`verify.cpp` runs V10 reference fallback/fused outputs and current matcher
fallback/fused outputs over thread counts 1/4/2/4 and repeated calls. This is
useful ordered-output evidence for both paths, but there are two limitations:

- The current `search_experiment::options(7)` helper in the working tree freezes
  the historical experiment with `fused_local_search=false`. The working-tree
  `MatchOptions` has no `reuse_local_centers` member, and the center-cache draft
  is not wired into this verification. `verify.cpp` toggles
  `fused_local_search`, but it cannot exercise cache hits. Thus it does not
  verify consolidation after cache reuse. The separate local-center workspace
  test is the appropriate place to cover cache-on/off; this verification should
  not be described as a cache regression result.
- The V10 reference implementation is an independent source snapshot, but its
  exact output is used as the primary oracle. It cannot prove broad detection
  accuracy or behavior on unseen template banks.

The verification records both set equality and full ordered equality. It also
records a canonical-map equality and the first mismatch index. That catches a
minimum-ID or tie-order error that a set-only comparison would miss.

## Verification completeness and limitations

The independent oracle and unit test are strong for finite scalar records, but
the following cases are not covered by the reviewed files and should remain
explicit limitations:

- NaN, infinity, signed-zero and other injected nonstandard float values;
- duplicate keys spanning multiple class IDs in a real multi-class detector
  call (the hand test has classes A/B; the image verification selects one class);
- an adapter that derives different bounding boxes from competing template IDs;
- empty/all-zero real search maps through the full detector call;
- consolidation after center-cache hits (the cache is not an option in this
  `MatchOptions` verification path);
- a >2^31 vector size or allocator failure;
- concurrent calls sharing one `MatchWorkspace`, which the public workspace
  contract does not promise.

The reviewed `verify.cpp` also defaults to the tiny dataset unless a different
`--dataset` and template bank are supplied. Its normal full case count is 25
(the nine fixed fixtures plus 16 development images), while `--minimal` selects
one frozen frame. It is a regression/equivalence check, not a complete expanded
T-LESS evaluation. Held-out data must remain outside any parameter-selection
loop.

## Required claims

It is accurate to claim that the helper provides deterministic minimum-template
ID consolidation for finite `Match` records and that the checked call site
preserves matcher-level class/x/y/score semantic keys while defining an ordered
tie policy. It is not accurate to claim that this review proves adapter bounding
box equivalence, cache-on regression coverage in `verify.cpp`, general detection
accuracy, or performance improvement. Those require the corresponding adapter,
cache matrix, accuracy protocol, and uninstrumented benchmark evidence.
